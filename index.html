      Para decidir en equipo

      Cómo se midió la dificultad

      • Baja: el backend ya filtra y falta el control, o basta sumar un parámetro sobre una columna del mismo modelo; las opciones ya existen y ningún reporte obliga a cambios.
      • Media: filtro sobre una relación, rango de fechas o valor derivado, o hay un reporte o exportación dentro del mismo backend que debe alinearse.
      • Alta: el listado sale de SQL propio o de una vista de base de datos, el endpoint lo comparten otros flujos, falta una definición, o la consistencia depende de un reporte que vive en otro servicio.

      Qué significa el impacto en reportes

      • Sin impacto: ningún reporte usa ese dato.
      • Hay que alinear: un reporte o exportación usa el mismo dato; el filtro debe usar los mismos valores y la misma regla, o el reporte debe recibirlo.
      • Bloquea: la consistencia depende de código que no está en los repos revisados o de una decisión previa.

      Cómo se van a pintar los filtros nuevos

      La mayoría de las vistas usa el componente genérico FilterTable, que solo ofrece Buscar, Estado y Ordenar por, y no admite controles adicionales. Cada filtro nuevo obliga a elegir entre extender ese componente o hacer un filtro propio por vista. El detalle de cada vista indica cuál de los dos casos es.

      Alcance y método

      • Se revisaron las entradas del menú Configuración de Citas, Digiturno, Historia clínica, Inventarios, Facturación, Superadmin y Suscripciones, y todos los reportes del menú Reportes.
      • Pacientes, Médicos, Entidades afiliadoras, Sedes y Ocupaciones son una sola vista reutilizada en varios módulos.
      • «Línea tocada» es la fecha de git blame del campo en el formulario; un retoque de texto también la mueve.
      • Análisis estático de front y back, sin ejecutar la aplicación. Cada lote lo revisó un segundo lector contra el código ( correcciones entre las dos pasadas).
